## 2026-10-27 Audio: silent stretches, crackle, window drags, device changes

Runs: windowed, retail BIOS, 60 fps pacer, `SDL_AUDIODRIVER=dummy` unless noted (the dummy device pulls ~43.9k frames/s
instead of 44.1k, so its runs show a slowly rising ring fill and some overflow drops that a real device does not).
Tools: `PSXRT_AUDIO_STATS=1`, `PSXRT_AUDIO_WAV=<file>` (stubs/psxrt_audio.c), `audio_gaps.py` (maintainer tool outside the repo: counts 1-100 ms digital-silence dropouts inside loud audio).

**Where sound should exist (boot to title, no input):**

| Wall time | Screen (VRAM dumps every 3 s) | Audio |
|---|---|---|
| 2-13 s | SONY, PlayStation logo | BIOS jingle (SPU voices keyed) |
| ~9 s | (disc load) | guest runs at 15-25% speed for ~1.5 s: SPU output 5-12k frames/s, so the ring runs dry |
| 14-31 s | "SCEA presents", Enix, tri-Ace logos, mosaic | silent: the game keys **no** SPU voice (keyon=0, voices=0) with the SPU on and unmuted (SPUCNT 0xC083). Game-side silence, not an output fault |
| 31 s on | opening movie, then title | music, SPU voices keyed (3-13) |

- The STR movies carry no audio: every sector of the four disc-1 movies checked is a video sector (`0x0160 0x8001`
  header, 10 per frame), and each frame's bytes after the MDEC data are `0xFF` padding. Movie music is an SPU
  sequence the game plays from SPU RAM while the movie streams, so it does not touch the XA/CD-DA paths at all
  (8-bit XA being unsupported does not matter here).
- Not compared with real hardware: whether the logos are silent on a PS1 too is assumed from the key-on count only.

**Faults found and fixed (stubs/psxrt_audio.c, CMake patches in recomp/rtfull/CMakeLists.txt):**

1. *Crackle after any stall.* The DRC bridge stays primed after it runs dry, so it played each sample as it arrived
   on a near-empty ring (6 dry events in one second at the boot load) and the fill took ~30 s to climb back (the
   rate correction is capped at 0.5%). Now it re-primes to a third of the target before playing again (a full-target
   re-prime overflowed by 4135 frames because the pacer catches up faster than real time after a stall).
   150 s boot run: `audio_gaps.py` 26 dropout gaps -> 2 (both 1 ms); real device: no overflow after the boot load.
2. *Window drag silenced the game.* Windows runs its own message loop while the title bar is dragged, inside the
   emulation thread's event pump, so the emulation (and the guest-clocked SPU) stopped. The pump now runs on a second
   fiber; a 10 ms thread timer, which Windows also dispatches in the modal loop, switches back to the emulation. Two
   simulated 6 s drags (`WM_SYSCOMMAND SC_MOVE`, then Escape): before, 2 x 5.8 s of silence and SPU 0 frames/s; after,
   SPU 44k frames/s and 0 underruns. Real mouse drags and window resizing were not tried (same modal loop, unverified).
3. *Device changes.* The stream is opened on SDL's default logical device, so SDL already moves it when Windows
   changes the default. New: every device added/removed/format change is logged; if our device is removed, or stops
   pulling audio for 1.5 s while not paused, the stream is reopened on the default device (errors logged, retried every
   2 s). `PSXRT_AUDIO_TEST_REOPEN=12` on the real WASAPI device: three reopens in 40 s, 0 underruns, no gaps. A real
   KVM/USB unplug was not reproduced.

**Not fixed:** the boot disc load (~9 s) runs the guest at 15-25% speed for about 1.5 s, so the BIOS jingle has a gap
of about 1 s (one clean gap now instead of crackle). That is emulation speed, not audio output. Underruns also appear
when other heavy processes share the CPU (one 1-s dip to 58% guest speed in a shared-machine run).
